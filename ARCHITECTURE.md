# `concert_navigation` — Architecture & Inter-Package Interactions

> Implementation notes for the Nav2-based navigation stack of the **CONCERT**
> modular robot (HHCM / IIT, `forest_ws` ROS 2 workspace).
>
> Scope of this document: how `concert_navigation` is built, what it owns vs.
> what it only *orchestrates*, the full command and perception pipelines, the TF
> tree, and every sibling package it talks to. It also flags a few mismatches
> found while reading the code (see [§14](#14-observations--gotchas)).

---

## 1. Where the package actually lives

| Path | What it is |
|------|------------|
| `src/concert_navigation/` | **Real package source** (edit here). |
| `src/concert_navigation/concert_navigation/` | Inner package dir: `launch/`, `config/`, `behavior_tree/`, `package.xml`, `CMakeLists.txt`. |
| `build/concert_navigation/` | **CMake/colcon build artifacts only** — no source. Regenerated by `forest grow` / `colcon build`; do not edit. |
| `install/share/concert_navigation/` | Installed `launch/ config/ behavior_tree/` consumed at runtime via `get_package_share_directory`. |

`CMakeLists.txt` does **no compilation** — the package is pure config + launch:

```cmake
install(DIRECTORY launch config behavior_tree
        DESTINATION share/${PROJECT_NAME})
```

So everything this package "does" is expressed as launch wiring + YAML parameters
+ one Behavior Tree XML. All executables it runs come from upstream Nav2 packages
and sibling CONCERT packages.

---

## 2. Robot & workspace context

- **Robot:** CONCERT — a modular mobile manipulator with a **4-wheel omnidirectional
  ("omnisteering") base** (`wheel_A/B/C/D`), front & back **Velodyne VLP16** 3D
  LiDARs, RealSense D435i cameras, and an IMU.
- **Low level:** runs on **XBot2** (real-time, EtherCAT). The base accepts velocity
  commands on **`/omnisteering/cmd_vel`** (`geometry_msgs/Twist`).
- **Workspace:** an **HHCM Forest** workspace; built with `forest grow <project>`.
  ROS 2 on Ubuntu 24.04 Noble (per the Docker base `hhcmhub/xbot2-noble-dev`,
  i.e. ROS 2 Jazzy).
- **Key contract** (from `README.md`): `concert_navigation` is the **real-robot**
  Nav2 bringup and assumes the base/odometry/scan stack is *already running*:
  - `/omnisteering/cmd_vel` — `geometry_msgs/Twist` (base input)
  - `/base_link/odom` — odometry
  - `/scan` — fused 2D laser scan
  - TF frames `map`, `odom`, `base_link` available

      (obstacle_layer)       (obstacle_layer)     (scan source)        (localize)       (mapping)
            │                       │                                      │                │

      planner_server ───path──> controller_server (MPPI, Omni)            (one of the two provides it)
            ▲                       │ cmd_vel  (remap → cmd_vel_nav)

## 4. Package layout

```
concert_navigation/concert_navigation/
├── launch/
│   ├── path_planner.launch.py              # THE Nav2 bringup (7 nodes + lifecycle mgr)
│   ├── master_lidar_conversion_fuse.launch.py   # cloud→scan + scan merge → /scan (1 or 2 lidars)
│   ├── master_cloud_multi_merger.launch.py      # 3D cloud merge → /merged_cloud (1 or 2 lidars)
│   └── master_mapping_slam_saver.launch.py      # SLAM + map saver (delegates to concert_mapping)
├── config/
│   ├── controller.yaml          # MPPI controller + costmap-independent controller_server params
│   ├── planner_server.yaml      # Smac 2D planner
│   ├── global_costmap.yaml      # map-frame costmap (static + obstacle + inflation)
│   ├── local_costmap.yaml       # odom-frame rolling costmap (voxel + inflation)
│   ├── bt_navigator.yaml        # BT navigator (navigate_to_pose only)
│   ├── smoother_server.yaml     # path smoother (simple_smoother)
│   ├── velocity_smoother.yaml   # output velocity ramping/limits
│   ├── collision_monitor.yaml   # final safety gate → /omnisteering/cmd_vel
│   └── recovery.yaml            # behavior (recovery) server
└── behavior_tree/
    └── behavior.xml             # navigate-to-pose BT with replanning + recovery
```

The three `master_*` launch files are **thin orchestrators**: they only
`IncludeLaunchDescription` other packages' launch files (and forward
`use_sim_time`). `path_planner.launch.py` is the only one that defines real nodes.

## 5. `path_planner.launch.py` — the Nav2 core

Brings up **7 managed nodes + 1 lifecycle manager**. All share `use_sim_time`
(default from env `USE_SIM_TIME`, else `false`) and remap `/tf,/tf_static` →
`tf,tf_static`.

| # | Node (name) | Package / executable | Key config | cmd_vel remap |
|---|-------------|----------------------|------------|----------------|
| 1 | `controller_server` | `nav2_controller` | `controller.yaml` **+ `local_costmap.yaml`** | `cmd_vel → cmd_vel_nav` (pub) |
| 2 | `planner_server` | `nav2_planner` | `planner_server.yaml` **+ `global_costmap.yaml`** | — |
| 3 | `recoveries_server` | `nav2_behaviors/behavior_server` | `recovery.yaml` | `cmd_vel → cmd_vel_nav` (pub) |
| 4 | `bt_navigator` | `nav2_bt_navigator` | `bt_navigator.yaml` + `default_nav_to_pose_bt_xml = behavior.xml` | — |
| 5 | `velocity_smoother` | `nav2_velocity_smoother` | `velocity_smoother.yaml` | `cmd_vel → cmd_vel_nav` (**sub**) |
| 6 | `collision_monitor` | `nav2_collision_monitor` | `collision_monitor.yaml` | — (uses in/out topic params) |
| 7 | `smoother_server` | `nav2_smoother` | `smoother_server.yaml` | — |
| — | `lifecycle_manager_navigation` | `nav2_lifecycle_manager` | `autostart: true`, manages the 7 above | — |

Notes:
- The **costmaps are not separate nodes here**. The local costmap params are loaded
  *into* `controller_server`, and the global costmap params *into* `planner_server`
  (Nav2 runs each costmap inside its owning server).
- Param-merge order matters: e.g. `parameters=[controller_yaml, {'use_sim_time':…}, local_costmap_yaml]`.
  The launch-supplied `use_sim_time` overrides the `use_sim_time: False` baked into
  the YAMLs (later entries win for the same key).
- Lifecycle manager **autostarts** all nodes (configure→activate) in listed order.

## 6. Command pipeline (`cmd_vel`) — the most important wiring

This is the chain the README calls out, and only **`collision_monitor`** is
allowed to publish to the base:

```text
controller_server ─┐
                   ├─► cmd_vel_nav ─► velocity_smoother ─► cmd_vel_smoothed ─► collision_monitor ─► /omnisteering/cmd_vel
recoveries_server ─┘                                                                                       (base)
```

How the topic names actually resolve (via remaps + node params):

| Stage | Subscribes | Publishes | Mechanism |
|-------|-----------|-----------|-----------|
| `controller_server` | (path/odom) | **`cmd_vel_nav`** | remap `cmd_vel→cmd_vel_nav` |
| `recoveries_server` | — | **`cmd_vel_nav`** | remap `cmd_vel→cmd_vel_nav` |
| `velocity_smoother` | **`cmd_vel_nav`** | `cmd_vel_smoothed` | remap on input `cmd_vel→cmd_vel_nav`; output is its default `cmd_vel_smoothed` |
| `collision_monitor` | `cmd_vel_smoothed` | **`omnisteering/cmd_vel`** | params `cmd_vel_in_topic` / `cmd_vel_out_topic` |

So controller **and** recovery behaviors both feed the *same* `cmd_vel_nav`
(only one is active at a time). All commands are `geometry_msgs/Twist`
(`enable_stamped_cmd_vel: false` everywhere).

**Debug ladder** (from README §Troubleshooting): if `cmd_vel_nav` has data but
`cmd_vel_smoothed` doesn't → suspect `velocity_smoother`; if `cmd_vel_smoothed`
has data but `/omnisteering/cmd_vel` doesn't → suspect `collision_monitor`.

## 7. Perception pipeline → `/scan`

Driven by **`master_lidar_conversion_fuse.launch.py`**. As of the single-lidar
robustness work this launch is **self-contained and parameterized** (it defines
the nodes directly instead of including the sibling launch files), so it works
with one OR two lidars:

```text
VLP16_lidar_front/velodyne_points ─► pointcloud_to_laserscan_front ─► /VLP16_lidar_front/scan ─┐ (if use_front_lidar)
VLP16_lidar_back /velodyne_points ─► pointcloud_to_laserscan_back  ─► /VLP16_lidar_back/scan  ─┤ (if use_back_lidar)
                                                                                               ▼
                                       ira_laser_tools::laserscan_multi_merger  ──────────►  /scan
                                       (laserscan_topics = ENABLED scans only)   (frame: first enabled lidar's _base_link)
```

Launch args: `use_front_lidar` / `use_back_lidar` (default `true`),
`front_scanner` / `back_scanner` (namespaces), `use_sim_time`.

```bash
ros2 launch concert_navigation master_lidar_conversion_fuse.launch.py                       # both
ros2 launch concert_navigation master_lidar_conversion_fuse.launch.py use_front_lidar:=false  # back only
```

Step 1 — `pointcloud_to_laserscan` (one node per **enabled** lidar) flattens each
3D cloud into a 2D scan using **different height bands**:
- front: `min_height -0.5 … max_height 3.0`, `target_frame VLP16_lidar_front_base_link`, `scan_time 0.2`
- back:  `min_height -3.0 … max_height 0.5`, `target_frame VLP16_lidar_back_base_link`, `scan_time 0.05`
- both: full 360° (`±π`), `angle_increment 0.007`, `range 0.7–10.0`, `use_inf:true`

Step 2 — `ira_laser_tools::laserscan_multi_merger` merges the enabled scans →
**`/scan`** (`range 0.9–130`, `angle_increment 0.007`), in the first enabled
lidar's `_base_link` frame (front when present, else back).

> ⚠️ **Why the merger must only list enabled topics.** `laserscan_multi_merger`
> (a) blocks in its constructor (`while(!tokens.empty())`) until *every* topic in
> `laserscan_topics` is advertised, and (b) only publishes once a fresh scan from
> *every* subscribed topic has arrived (`totalClouds == clouds_modified.size()`).
> So if a dead lidar is left in the list, `/scan` is **never** published and the
> whole stack stalls. The launch builds `laserscan_topics` from the enabled
> lidars only — that is the core single-lidar fix.

`/scan` is then consumed by: global costmap `obstacle_layer`, local costmap
`voxel_layer`, `collision_monitor` (`scan` source), **AMCL**, and **slam_toolbox**.

### Alternate 3D cloud path
`master_cloud_multi_merger.launch.py` merges the 3D point *clouds* (for 3D
mapping / RTAB-Map style use) → `/merged_cloud`, parallel to the 2D scan path.
Also parameterized by `use_front_lidar` / `use_back_lidar`. It runs
`perception_utils_ros2`'s `pointcloud_merger` (which skips empty clouds, so it is
inherently single-lidar tolerant). Previously this file was broken — see
[§14](#14-observations--gotchas) item 1.

## 8. TF tree & frames

```text
        map
         │   ← published by AMCL (saved-map mode)  OR  slam_toolbox (SLAM mode)
        odom
         │   ← published by concert_odometry (base_estimation, publish_tf:true)
     base_link
       ├──(URDF static, z = −0.747) ── base_link_projected   ← 2D base frame for AMCL & slam_toolbox
       ├──(URDF) ── VLP16_lidar_front_base_link              ← /scan frame
       └──(URDF) ── VLP16_lidar_back_base_link
```

Frame usage by node (note the deliberate split):

| Node / file | `global_frame` | `robot_base_frame` | `odom` topic |
|-------------|----------------|--------------------|--------------|
| `bt_navigator` | `map` | `base_link` | `/base_link/odom` |
| global costmap | `map` | `base_link` | — |
| local costmap | `odom` | `base_link` | — |
| `controller_server` | — | — | `/base_link/odom` |
| `velocity_smoother` | — | — | `/base_link/odom` (CLOSED_LOOP) |
| `collision_monitor` | — | `base_frame_id: base_link`, `odom_frame_id: odom` | — |
| **AMCL** | `map` | **`base_link_projected`** | (uses TF) |
| **slam_toolbox** | `map` | **`base_link_projected`** | (uses TF) |
| EKF (`ekf.yaml`, alt.) | `map` | **`base_footprint_ekf`** | `base_link/odom` |

> `base_link_projected` is the **ground projection** of `base_link` (URDF fixed
> joint, 0.747 m down). AMCL and slam_toolbox do 2D matching against this
> projected frame, while wheel odometry drives `odom→base_link`. `base_footprint_ekf`
> belongs only to the alternative `robot_localization`/EKF pipeline (see §9).

## 9. Localization vs SLAM

`concert_navigation` itself does **not** start `map_server`, AMCL, or SLAM. It
relies on a sibling package providing `map→odom`. There are three relevant modes:

**A. Saved-map navigation (primary real-robot flow)** — `concert_localization/localization.launch.py`:
- `nav2_map_server` (serves the saved map)
- `nav2_amcl` (`amcl_config.yaml`): `OmniMotionModel`, `likelihood_field`,
  `base_frame_id: base_link_projected`, `tf_broadcast: true` → provides `map→odom`.
- its own `lifecycle_manager_localization` (manages `map_server`, `amcl`).
- Map path is built as `concert_mapping/maps/<map_name>/myworld.yaml`
  (arg `map_name`, default `map_test`). ⚠️ README shows a `map_file:=…` arg that
  this launch does not define — see [§14](#14-observations--gotchas).

**B. SLAM / mapping** — `concert_navigation/master_mapping_slam_saver.launch.py`
delegates to `concert_mapping`:
- `slam_toolbox_sync.launch.py` → `sync_slam_toolbox_node` (`slam_toolbox_config.yaml`,
  `mode: mapping`, `base_frame: base_link_projected`) → provides `map→odom` + the map.
- `map_saver.launch.py` → `map_saver_server` (save via `map_saver_cli`).

**C. EKF odometry fusion (alternative, `local_localization.launch.py`)** — runs
`robot_localization` `ekf_node` (`ekf.yaml`, `two_d_mode`, fuses `base_link/odom`
+ IMU `imu_ekf`), an `imu_republisher`, and a static `base_footprint_ekf→imu_link_ekf`.
This is a different odometry/fusion option and is **not** the AMCL map→odom source.

Either A or B supplies `map→odom`; Nav2 (this package) is mode-agnostic and just
needs that transform + `/scan` + `/base_link/odom`.

## 10. Costmaps

Both share the robot **footprint** `[[-0.685,-0.4],[-0.685,0.4],[0.685,0.4],[0.685,-0.4]]`
(≈1.37 m × 0.8 m), `footprint_padding 0.03`, `resolution 0.05`, inflation
`cost_scaling_factor 3.0` / `inflation_radius 0.7`.

| | **global** (`global_costmap.yaml`) | **local** (`local_costmap.yaml`) |
|--|------------------------------------|----------------------------------|
| frame | `map` | `odom`, `rolling_window`, 5×5 m |
| update / publish | 1.0 / 1.0 Hz | 5.0 / 2.0 Hz |
| layers | `static` + `obstacle` + `inflation` | `obstacle` + `inflation` |
| obstacle src | `/scan` (LaserScan) | `/scan` (LaserScan) |
| raytrace / obstacle range | 3.0 / 2.5 m | 3.0 / 2.5 m |
| min/max obstacle height | `-0.3 … 2.0 m` (layer + source) | `-0.3 … 2.0 m` (layer + source) |
| unknown space | `track_unknown_space: true` | default free (no z-window) |

Lives inside `planner_server` (global) and `controller_server` (local) — there
are no standalone costmap nodes. Cleared by BT recovery via
`global_costmap/clear_entirely_global_costmap` /
`local_costmap/clear_entirely_local_costmap`.

> ⚠️ Both obstacle layers carry **`min_obstacle_height: -0.3` at BOTH the layer level
> and the `scan` source** (see `DEBUG_FINDINGS.md` A1, verified live): the `/scan` plane
> sits at z=−0.063 m in `odom`/`map`, and Nav2's default `0.0` height gates would
> otherwise discard every point → empty costmaps. The local costmap uses `ObstacleLayer`
> (not `VoxelLayer`), and `width`/`height` must be **integers** (A10) or
> `controller_server` crashes on configure.

## 11. Planner, controller, smoother, recoveries

**Planner** (`planner_server.yaml`) — `nav2_smac_planner::SmacPlanner2D`
(`GridBased`): `tolerance 0.5`, **`allow_unknown: false`** (safer for saved maps;
flip to `true` for live SLAM through unknown space), `max_planning_time 2.0`, plus
an internal smoother.

**Controller** (`controller.yaml`) — `nav2_mppi_controller::MPPIController`
(`FollowPath`). This is the core **omni-drive** tuning:
- `motion_model: "Omni"`, `vx_max 0.5`, **`vy_max 0.5`** (lateral!), `wz_max 0.8`,
  `vx_min -0.35`; accels `ax/ay 2.0`, `az 1.2`.
- `controller_frequency 20 Hz`, `batch_size 2000`, `time_steps 56`, `model_dt 0.05`.
- Critics: Constraint, Cost (footprint-aware), Goal, GoalAngle, PathAlign,
  PathFollow, **PathAngle (`mode:1` = NoDirectionalPref, omni)**, PreferForward,
  Twirling, VelocityDeadband.
- `general_goal_checker`: `xy_goal_tolerance 0.25`, `yaw_goal_tolerance 0.25`.
- `progress_checker`: `required_movement_radius 0.5` within `10 s`.

**Path smoother** (`smoother_server.yaml`) — `nav2_smoother::SimpleSmoother`
(`simple_smoother`), invoked from the BT after planning.

**Velocity smoother** (`velocity_smoother.yaml`) — `max_velocity [0.5, 0.5, 0.8]`,
`min [-0.5,-0.5,-0.8]`, accel `[2,2,1.2]`, `CLOSED_LOOP` (uses `/base_link/odom`),
`deadband [0.05,0.05,0.05]`. **Nonzero Y limits ⇒ omni** (a differential config
would have Y=0).

**Recoveries** (`recovery.yaml`) — `behavior_server` with
`spin / backup / drive_on_heading / assisted_teleop / wait`; spin limited to
`max_rotational_vel 0.4`, `rotational_acc_lim 0.6` (intentionally slowed vs Nav2
defaults).

## 12. Behavior Tree (`behavior_tree/behavior.xml`)

`navigate_to_pose` only (navigate_through_poses is disabled in `bt_navigator.yaml`).

```text
RecoveryNode (retries=6)  "NavigateRecovery"
├─ PipelineSequence "NavigateWithReplanning"
│  ├─ RateController (1 Hz)
│  │   └─ RecoveryNode (retries=1) "ComputePathToPose"
│  │      ├─ Sequence: ComputePathToPose(GridBased) → SmoothPath(simple_smoother)
│  │      └─ Fallback:  GoalUpdated? | ClearGlobalCostmap
│  └─ RecoveryNode (retries=1) "FollowPath"
│     ├─ FollowPath(controller=FollowPath, goal_checker=general_goal_checker)
│     └─ Fallback: GoalUpdated? | ClearLocalCostmap
└─ ReactiveFallback "RecoveryFallback"
   └─ GoalUpdated? | RoundRobin[ ClearBothCostmaps , Spin(1.57) , Wait(5s) , BackUp(0.15m @0.025) ]
```

Plan is recomputed at 1 Hz and re-smoothed; per-step failures clear the relevant
costmap; persistent failure escalates to the round-robin recovery set. Error codes
(`compute_path_error_code`, `smoother_error_code`, `follow_path_error_code`) are
surfaced via `bt_navigator.yaml`.

## 13. Collision monitor — final safety gate

`collision_monitor.yaml` is the last stage before the base. Input
`cmd_vel_smoothed`, output `omnisteering/cmd_vel`, source `/scan`. (Its
`min_height 0.15`/`max_height 2.0` are **ignored** — Nav2 `Scan` sources are 2D and
read no height; only `PointCloud` sources would. See `DEBUG_FINDINGS.md` A11.) Three
layered polygons (in priority order):

| Polygon | Size (m) | Action | Notes |
|---------|----------|--------|-------|
| `PolygonStop` | 1.5 × 1.0 | **stop** | hard stop if ≥4 points inside |
| `PolygonSlow` | 1.9 × 1.3 | **slowdown** | scale to `0.4×` |
| `FootprintApproach` | live footprint | **approach** | time-to-collision `1.2 s`, uses `/local_costmap/published_footprint` |

`source_timeout 1.0`, `stop_pub_timeout 2.0`, `base_shift_correction: true`.

## 14. Observations & gotchas

Things worth knowing before relying on the docs/launches verbatim:

0. **Costmap fixes verified live (2026-06-04).** The local costmap was empty on the real
   robot for two stacked reasons — a `width/height` type crash (`controller_server` exit
   −6) and a sub-zero `/scan` plane (z=−0.063 m) rejected by the costmap height gates
   (including the easily-missed **layer-level** `min_obstacle_height`). Both fixed and
   confirmed live; see `DEBUG_FINDINGS.md` A1/A5/A10/A11/A12 and §E for the full trace.

1. **`master_cloud_multi_merger.launch.py` used to include a non-existent file**
   (`ira_laser_tools/launch/cloud_multi_merger.launch.py`; `ira_laser_tools` only
   ships ROS 1 `.launch` files). **Fixed:** it now runs `perception_utils_ros2`'s
   `pointcloud_merger` directly. While fixing it, two more latent bugs in the old
   `perception_utils_ros2/cloud_multi_merger.launch.py` defaults were corrected:
   the input topic was `…/points` (real topic is `…/velodyne_points`) and
   `destination_frame` was `VLP16_lidar_back` (not a published TF frame; now
   `<scanner>_base_link`).

8. **`laserscan_multi_merger` will stall the whole stack if any listed scan topic
   is missing.** Its constructor blocks until every `laserscan_topics` entry is
   advertised, and it only publishes `/scan` once every subscribed topic has
   delivered a fresh scan. This is why running with a dead lidar (e.g. front off)
   froze `/scan`. **Fixed** by `master_lidar_conversion_fuse.launch.py` now
   feeding the merger only the *enabled* lidars' scans
   (`use_front_lidar` / `use_back_lidar`). The `pointcloud_to_laserscan` nodes
   themselves are independent and never blocked — only the merger did.

2. **README localization command vs. actual args.** README §5 shows
   `localization.launch.py map_file:=/abs/path/map.yaml`, but the launch defines
   **`map_name`** (default `map_test`) and **`amcl_config`**, not `map_file`. The
   map path is hard-wired to `concert_mapping/maps/<map_name>/myworld.yaml`. A
   `map_file:=` arg is silently ignored.

3. **`use_sim_time` defaults are inconsistent across packages.** Navigation
   launches default to env `USE_SIM_TIME` → `false`. But
   `localization.launch.py` and `amcl_config.yaml` default to **`true`**, and
   `slam_toolbox_sync.launch.py` defaults to `false`. On the real robot you must
   pass `use_sim_time:=false` to localization (the README does). Launch-level
   params override the YAML values where both set it.

4. **Forest project name.** README says `forest grow concert_nav2`, but the
   package is `concert_navigation`. The README notes to substitute the actual
   project name — just be aware they differ.

5. **Odometry is wheel-only by default.** `base_estimation_params.yaml` has
   `use_imu: false`; odometry (`concert_odometry` = `base_estimation_node`) fuses
   the 4 rolling wheel contacts and publishes `odom→base_link`. IMU fusion exists
   only in the separate EKF pipeline (`local_localization.launch.py`).

6. **`base_link_projected` must exist in TF** for AMCL/slam_toolbox to work. It
   comes from the robot URDF (`modular .../concert.sensors.urdf.xacro`,
   `base_link_projected_joint`, z = −0.747), published by `robot_state_publisher`
   in the XBot2/description bringup — outside this package.

7. **Map file location.** `concert_mapping` ships both `maps/myworld.yaml` and
   `maps/map_test/myworld.yaml`; the default `map_name: map_test` resolves to the
   latter. (A code comment claims it "does not exist" — it does.)
